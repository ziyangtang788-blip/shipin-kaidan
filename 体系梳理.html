01这家公司到底在干什么

一句话:一个数据转换器 + 一个搬运和分拣的动作。

公司不生产任何东西。所有商品都是从供应商买进来,原样(或分装后)送到客户手上。所以整个系统的本质是:

客户的「订货需求」 ──转换──→ 我们的「采购需求」 ──转换──→ 客户的「送货单」 │ 中间只经过: 收货 · 分拣 · 装车 不经过任何加工

角色关系

角色是谁在系统里
供应商批发市场档口、农户、厂家、二级批发商我们向他们下采购单
我们食品配送公司系统的主人。只流通,不生产
客户餐厅、食堂、学校、超市、小配送商他们向我们下单,我们出销售单/送货单

一天的实际流程

D 日下午 ① 收单 客户微信发文字/拍照/Excel │ ↓ │ 录单台(三层识别)→ 人工核对 ✔ → 销售单 │ D 日 18:00 ② 截单 过点的单算后天 │ ↓ D 日晚 ③ 汇总 所有客户明日需求,按 SKU 合并 │ ↓ 减可用库存 / 加安全库存 / 按规格取整 │ 采购建议 → 按供应商拆 → 采购单 → 发给供应商 │ D+1 凌晨 ④ 到货 过磅、验收、记实际采购价(每天都在变) │ ↓ │ ⑤ 分拣 按客户把大堆货分成小份 │ ↓ 实际称重 → 记实发量 │ 缺货 → 记缺发 / 换替代品 │ ↓ │ ⑥ 装车 按路线排车 → 打印送货单 │ D+1 早 ⑦ 配送 送达 → 签收(拍照/签字) │ ↓ 月底 / 周期 ⑧ 对账 按结算量 × 单价出对账单 → 收款 ⑨ 付款 按实际采购金额付供应商
系统的核心价值只在两个转换点 转换点一:客户的人话 → 我们的结构化订单(第 ① 步,AI 在这里)
转换点二:N 张客户订单 → M 张供应商采购单(第 ③ 步,纯算法)
其余环节都是记录和打印。这两个点做好了,系统就成立了。

02五条真难点

难点一:客户叫法 ≠ 系统商品名

同一个东西,10 个客户有 10 种写法。有的还是简称、错别字、方言。

→ customer_alias 表,按客户分,同时支持"全局叫法"(一家教会全网通用)。这是系统最值钱的资产,越用越准。

难点二:点位号拆行 + 点位调价

同一个客户、同一个商品,送到不同门店/点位要拆成不同的行,而且不同点位可能有不同的价格调整。

→ 销售单行带 spot_code;spot_rule 表存每个客户的点位调价规则。规则化,不写死在代码里。

难点三:订货量 ≠ 实发量 ≠ 结算量 ⚠️

这是生鲜配送最要命的一条,也是普通进销存软件最不适配的地方。

字段什么时候产生例子
qty_order客户下单时订 10 斤五花肉
qty_pick分拣称重时实际称出 10.3 斤
qty_settle结算规则决定按实际 10.3 结,还是按订货 10 结?因客户而异

→ 销售单行必须是三个数量字段,不是一个。客户档案上要有「按订货量结 / 按实发量结」的开关。
散装称重品(肉、菜)几乎不可能对得上;标品(整箱牛奶)才三个数相等。

难点四:缺货与替代

凌晨去市场没买到,或者品质不行。要么少发,要么换个近似品。这个决定发生在分拣台,不是办公室。

→ 分拣环节要能记「缺发」和「替代为某某」,并自动回写销售单行、影响结算金额和客户对账单。不能事后手工补,一定会漏。

难点五:采购价天天变

市场价一天一个样,甚至一天两个价。毛利不能按固定成本算。

→ 每次到货记这一批的实际采购价,毛利 = 结算金额 − 该批实际采购成本。
另外要有「进价异动提醒」:今天某个品进价比 7 天均价高 30% 以上,提示是不是该调客户售价了。

因为没有生产,库存的地位要重新摆 生鲜配送大部分商品是越库直发:今天订、明天凌晨采、分拣完直接装车,根本不入库过夜。只有冻品、干货、调料、包材才真正走库存。
→ SKU 上要有个标记:直采(越库) / 备货(走库存)。两类的采购算法完全不同(见第 06 节)。
→ 意味着库存模块没有想象中重要,分拣模块才是重头。v1 把重心放反了。

03识别三层漏斗(旧引擎直接复用)

昨晚那个 引擎-解析.js 可以直接搬过来,而且应该放在 AI 前面,当第一道闸。

旧引擎里哪些能用

能力跟卖什么货有关吗结论
全角转半角、去空格、括号统一无关✅ 直接用
识别并跳过表头 / 分隔线 / 页码 / 签名栏无关✅ 直接用
点位号 + 数量提取(支持三种写法)无关✅ 直接用,这块最值钱
Excel 粘贴后自动认表头列无关✅ 直接用
续行合并(商品名在上一行)无关✅ 直接用
同名不同单位自动拆成两行无关✅ 直接用
单位表里写死的「板 / 中板 / 大板 / 小板」有关(豆腐专用)⚠️ 改成从数据库读单位表
写死的分类词「豆制品 / 粉面制品 / 豆腐类」有关⚠️ 改成读 category 表

要改的只有两处常量,不是逻辑。工作量约半天。

三层漏斗

客户发来的一段文字 / 一张图 │ ├─ 第一层 对照表精确命中 ────────→ 直接出单 免费 · 0 延迟 │ 整段先跟 customer_alias 做精确匹配 │ 全部命中 → 根本不往下走 │ 【老客户的固定格式,大部分走这条】 │ ├─ 第二层 正则引擎(昨晚那个) ────→ 直接出单 免费 · 0 延迟 │ 格式规整、但叫法没见过的 │ 切出行 → 再回第一层匹配叫法 │ └─ 第三层 AI ────────────────────→ 出单 + 挂起人工确认 乱写的、拍照的、新客户第一次 【只有这一层花钱】
这个设计省下的钱 跑顺之后,真正落到 AI 的应该只有一两成单量。
按 100 单/天算:全走 AI 是 ¥300–960/月;走三层漏斗之后,大概 ¥60–150/月。
再叠加提示词缓存(同一客户的商品清单做缓存前缀,重复读 1/10 价),还能再降。

AI 的职责边界(不能破)

交给 AI交给确定性代码
做什么把乱的文字/图片切成结构化的行:
{原文, 客户叫法, 数量, 单位, 点位号, 备注}		叫法 → SKU 匹配
取该客户专属价
点位规则调价
金额、库存、结算全部计算
错了会怎样某行没认出 → 高亮挂起 → 人点一下 → 学会了不会错。规则是死的
要人工确认吗要。必须过人眼才能转正式单不用

AI 绝不碰钱。它认错顶多是一行商品挂起,永远不可能凭空编出一个价格。

06销售 → 采购 → 分拣 的算法

第一步:汇总出采购需求(每天一次,截单后跑)

  1. 取单 —— 送货日 = 明天、状态 ≥ 已确认的所有销售单行。
  2. 按 SKU 汇总 —— 合并所有客户的订货量。
  3. 分流 —— 按 SKU 上的采购模式走两条不同的路:
    直采(越库)备货(走库存)
    典型商品蔬菜、鲜肉、水产、豆制品冻品、干货、调料、包材、饮料
    建议采购量= 需求量(可加损耗率)= 需求量 − 可用库存 + 安全库存
    过不过夜不过夜,到货即分拣入库,按需出
  4. 取整 —— 按包装规格(整箱/整件)、供应商起订量向上取整。
  5. 出采购建议 —— 一张可编辑清单,采购员可手工调数量、换供应商。
  6. 拆单 —— 按每行指定的供应商拆成多张采购单 → 打印 / 导出 / 发微信。
v1 里那个 BOM 展开这里不需要了 公司不生产,没有"把豆腐炸成黄豆"这一步。需求汇总就是采购量,链路短一截,也少一个最容易出错的环节。

第二步:到货 → 分拣(次日凌晨)

  1. 到货验收 —— 录实际到货量 + 实际进价(这是当天真实成本,毛利靠它)。进价异常自动提醒。
  2. 生成分拣任务 —— 系统把"一大堆货"按客户炸开成"每家该拿多少"。
    可按两种方式组织:按商品拣(一个品拣完所有客户,适合称重品)或 按客户拣(一家一家配齐,适合标品)。两种都要支持。
  3. 称重录实发量 —— 手机/平板扫码 → 输入实际重量 → 写入 qty_pick。
  4. 处理异常 —— 缺货(记缺发数量)或替代(选另一个 SKU),当场记录,自动回写销售单行。
  5. 结算量落定 —— 按客户档案上的结算方式,qty_settle 取订货量或实发量。

第三步:装车 → 配送 → 签收

按路线排车次 → 打印送货单(打的是结算量和金额)→ 司机手机上看站点 → 送达拍照签收。

第四步:对账

客户对账单 = 期间内所有已签收销售单的 qty_settle × 单价。
毛利 = 结算金额 − 对应批次的实际采购成本(不是标准成本)。

07技术选型

层选型为什么
数据库PostgreSQL 16多人并发、事务可靠、JSONB 存识别中间结果、中文全文检索。不要 SQLite —— 多人同时开单会锁
后端Node.js + TypeScript + Fastify + Prisma和前端一套语言,旧代码也是 JS,正则引擎能原样移植。Prisma 自带迁移工具,对"不断更新"很关键
前端Vue 3 + Vite + Element Plus后台管理组件最全,表格/表单/打印现成。分拣和司机端要在手机上用,响应式必须做
反向代理Caddy自动 HTTPS 证书。手机拍照录单、扫码分拣必须 HTTPS
部署Docker Compose一条命令起全套,换服务器不用重配环境

09分期落地节奏

期做什么做完能干嘛
一期数据库 + 主数据(客户/商品/SKU/单位/专属价)+ 老数据导入价格库进系统了,能查了
二期录单台三层识别(移植旧正则引擎 + 对照表 + AI 兜底)+ 销售单 + 打印送货单手工敲单这件事没了 —— 最痛的点先解决
三期每日汇总 + 采购建议 + 采购单 + 到货验收(记实际进价)销售自动变采购,进价有账了
四期分拣模块(手机端称重、缺货替代)+ 结算量落定 + 排车配送签收实发量准了,对账不再扯皮
五期对账单 + 收付款 + 毛利报表 + 库存(备货型商品)全套闭环,能算清赚多少
六期客户自助下单入口、权限细分、进价异动提醒客户自己下单,连录单都省了

二期做完就已经能明显提效了,不用等全套。

10要你拍板的五件事

#问题影响什么
1只给这一家配送公司用,还是将来要卖给多家?多家的话每张表都要加"公司ID",登录、数据隔离全不一样。现在加几乎不费事,后加是整库重做
2他们的货,称重品占多大比例?(菜肉水产 vs 标品)决定分拣模块的分量、要不要接电子秤、手机端怎么设计。这条现在最影响工作量
3服务器放国内还是香港?决定要不要备案、AI 怎么接、访问速度
4几个人同时用?分拣和司机要不要用手机?决定服务器配置、权限设计、移动端投入
5老数据要迁多少?(只迁客户+商品+价格,还是连历史订单)决定一期工作量,也决定"同名多价靠历史消歧"能不能一上线就生效

第 1 题最要紧 —— 哪怕现在只自己用,只要将来有一点可能卖给别家,现在就该按多公司设计,成本只是多一个字段。
第 2 题其次 —— 称重品占比高,分拣就是重头戏,四期得往前提;全是标品的话,分拣可以做得很轻。
